psport v0.1.3

libSceNet starts from libSceNpManager's module start, draw preparation resyncs with the GPU thread's
registers (#887, #888), the loader reports imports that match only ignoring versions (#881), and the
Windows groundwork gets a test package with a probe of GPU memory sharing (#899). Windows is still
groundwork, not a supported platform: nothing in this version runs a game there, and `psport.exe`
does not start from the public package (FFmpeg, see below). No change to the launch interface; the
only new variable, `PS_LOOSE_IMPORT_VERSIONS`, is off by default.

Network (`src/system/runtime_np.c`, `src/loader/loader_link.c`, `src/kernel/runtime_module.c`)
- `runtime_np_manager_start` (once per process, `pthread_once`): `net_init`, `net_pool_create`
  `"SceNpSdkClient"` (0x4000 bytes, id `NET_POOL_ID_BASE` 3000), `ssl_init` (0x40000 bytes, context
  id 1), `http_init`; logs `Runtime: libSceNpManager started: net pool %d, SSL context %d, HTTP
  context %d`. A pool created afterwards (NpToolkit2's) gets 3001 and the next SSL context 2.
- Called before the module start of the first module whose imports list `libSceNpManager`
  (`needs_np_manager`, `has_np_manager_dependency` in `RuntimeModule`), and for the eboot only when
  libSceNpManager is not linked as a system module, which runs its own module start.
- `net_pool_create` and `net_pool_destroy` fail with `NET_ERROR_ENOTINIT` (0x804101C8, errno 200)
  before `net_init`, so a process that does not link libSceNpManager keeps the answer it had;
  `sceNetPoolCreate` also checks name (`CB_NET_POOL_NAME` 32), size (`CB_NET_POOL_MIN` 0x1000) and
  flags (`NET_ERROR_ENAMETOOLONG`, `NET_EINVAL`), 32 pools (`NET_ERROR_ENFILE`); 128 SSL contexts.
- `sceNetInit`, `sceNetTerm`, `sceNetPoolDestroy` and `sceSslTerm` stubs removed from
  `runtime_services.c`; `net_term` answers 0 and leaves the library initialized. First 16 failures
  logged (`log_library_failure`, `LOGGED_LIBRARY_FAILURES`), all counted in the call report.

Loader (`src/loader/loader_link.c`)
- Exact (NID, library, module, versions) binding unchanged. An import only an export of other
  versions would serve (`match_ignoring_versions`, index `versionless_map` keyed by NID, library
  and module names) is logged once: `Loader: import ... only ignoring versions: left to the host
  runtime (PS_LOOSE_IMPORT_VERSIONS=1 binds it)`; several candidate exports are `ambiguous` and never
  bound.
- `PS_LOOSE_IMPORT_VERSIONS=1` (`runtime_env_flag`, default 0) binds the single match. After the
  call report: `Loader: summary: <n> imports match an export only ignoring versions: <n> bound,
  <n> left to the host runtime (<n> ambiguous)`.
- Over 612 modules and games, none of 53 190 resolved imports matches only ignoring versions
  (kb #881): current games link as before.

GPU (`gpu/shadps4/video_core/renderer_vulkan/vk_draw_prep.cpp`, `gpu/diag/psport_srt_faults.cpp`)
- The draw preparation scanner (`ScanPacket`, `ScanCommands`) follows nested `INDIRECT_BUFFER`s up
  to `MaxNestedDepth` 4, copying them under a recovery point (`CopyGuestWords`) and keeping their
  state packets in `nested_words` for the workers. A buffer it cannot read, nesting deeper than 4
  and a `COND_EXEC` over packets that change registers end the scan of that buffer
  (`is_end_known` false): its later draws are not prepared.
- `RebaseTail` (`m_tail_epoch`, `m_is_tail_known`) takes the GPU thread's registers: after a buffer
  with unknown end state, and when `start_checksum` differs from the GPU thread's register checksum
  (a compute queue writing SH registers, anything not replayed), when the submissions from there are
  replaced by fresh copies and scanned again. The call-report line counts `resyncs after a buffer
  with unknown end state`, `after a register checksum mismatch` and `nested buffers replayed`.
- `SrtWalkerSignalHandler` (`flatten_extended_userdata_pass.cpp`): on a thread with
  `g_p_runtime_fault_recover` set (draw preparation workers, the draw pipe's table check) the fault
  abandons the walk and leaves the draw to the GPU thread (`PsSrtFaults::NoteAbandoned`,
  `AbandonedWalks`; counted in `SRT walker faults: summary: ... <n> speculative walks abandoned`,
  warning at every power of two).
- The diagnostic prints the load's effective address (`rdi` + displacement through
  `Common::GetRegister`, since a non-canonical address faults with 0) and both user data registers
  unmasked (`{:#018x}`).
- Octopath 0 (#888), measured in a test run of develop (not derivable from the tree): SRT walker faults 122728 to 0; prepared pipelines used 0 to 20578 of 21504
  (95.7%); 0 resyncs, 0 abandoned walks, 122044 nested buffers replayed. Bloodborne with 0 faults.

Windows platform (`gpu/memory/psport_guest_memory.cpp`, `src/platform/host_features.inc`)
- When the host import of the shared view fails, `ImportsPrivateMemory` tries private memory and
  the reason says so (`private memory imports: the driver takes anonymous memory only, and direct
  memory is mapped at several addresses through views of one shared memory`); the mode chosen is
  the same. The view is named `view of a section` on `_WIN32` and `memfd mapping` elsewhere.
- `host_features.inc`: `gpu_memory_host_import` `WIN32` `EXPERIMENTAL` (#870): under Proton on RADV the
  import of section views fails with `ErrorInvalidExternalHandle` and private memory imports; not
  run with a driver that imports views (NVIDIA, native Windows).

Windows test package (#899, all `EXPERIMENTAL`)
- `tools/win32_probe/` (`main.c`, `system.c`, `vulkan.c`, `memory_tests.c`, `probe.h`), built by
  `build.sh` as `out/psport-windows-probe.exe [--output PATH]`: writes
  `psport-windows-report.txt` next to the program (`%TEMP%` when not writable) with the system,
  each Vulkan device's capabilities and memory, and the tests of 1 MiB per device: `[a]` host import
  of private `VirtualAlloc` memory, `[b]` `MapViewOfFile` view of a pagefile section, `[b2]`
  `SEC_RESERVE` one, `[c]` `MapViewOfFile3` view in a placeholder, `[d]` two views of one section
  imported at once, `[e1]` `OPAQUE_WIN32`, `[e2]` `OPAQUE_WIN32_KMT`; an import passes when the GPU
  reads what the CPU wrote and the CPU sees what the GPU wrote. Ends with a verdict (`verdict_for`)
  on the guest-memory mode for the device psport takes.
- `tools/win32-bundle.sh DEST` writes `psport-windows-<version>-<commit>-x86_64.zip` and `.sha256`:
  `psport.exe`, `libpsport-gpu.dll`, `psport-gpu-capabilities.exe`, `psport-windows-probe.exe`,
  `psport-probe.bat`, `psport-probe.ps1`, `README-WINDOWS.txt` (`packaging/windows/`),
  `LICENSE.txt`, `THIRD-PARTY-NOTICES.txt`, `SOURCES.txt`, `BUILD-INFO.txt`, and the CLANG64 DLLs
  found from the PE import tables (`llvm-objdump`), each checked against an allowed-licence list
  of its MSYS2 package (GPL-2.0-compatible only).
- MSYS2's FFmpeg DLLs are left out (GPL-3.0-or-later, with x264, x265 and GnuTLS) together with what
  only they load: `psport.exe` does not start from the public package (`0xc0000135`), the probe
  does. `PS_BUNDLE_LOCAL=1` keeps them for a `-local` package for one's own machine, never
  redistributed. The online module stays out.
- `.github/workflows/windows.yml`: step `Bundle` runs `tools/win32-bundle.sh dist`; the zip is
  uploaded as the artifact as it is (`archive: false`, 14 days); a failed build uploads
  `psport-windows-logs-<sha>`. Never a release.
- `docs/en/WINDOWS_TEST.md`: how testers get the package, run `psport-probe.bat` and what the
  report holds; READMEs link it.
